---
title: Wire Protocol
lede: Binary wire protocol reference for the Flo client-server communication.
---

Clients talk to Flo over TCP on the client port (default **9000**) with a binary protocol: a fixed 32-byte header, then a payload. All integers are little-endian. The dashboard and metrics have their own HTTP ports.

## Request

### Header (32 bytes)

| Offset | Field | Type | Description |
|--------|-------|------|-------------|
| 0 | `magic` | `u32` | `0x004F4C46` (the bytes `F` `L` `O` `\0`) |
| 4 | `payload_length` | `u32` | Bytes of payload after the header |
| 8 | `request_id` | `u64` | Chosen by the client; the response carries it back |
| 16 | `crc32` | `u32` | CRC-32 of the header (this field excluded) and the payload |
| 20 | `op_code` | `u16` | The operation (see [OpCodes](#opcodes)) |
| 22 | `version` | `u8` | `0x02` |
| 23 | `flags` | `u8` | `0`: no flag is defined, and a request with any bit set is refused |
| 24 | `table_hash` | `u64` | The hash of the op table the client was built for |

### Payload

```
[namespace_len:u16][namespace][key_len:u16][key][value_len:u32][value][options_len:u16][options]
```

An empty namespace is the `default` namespace for most operations. Options are a sequence of `[tag:u8][len:u8][value]` entries (see [Options](#options)).

### Table ops

Every KV op is declared in the op table. Their payload has no value length and no options; the body is the rest of the payload:

```
[namespace_len:u16][namespace][key_len:u16][key][body]
```

The body is the op's fields, in order. A field that may be left out is a presence byte (`0` or `1`) and then its value; a field with a default is sent present. Integers are fixed-width; bytes have a length prefix as wide as their bound needs (`u8` up to 255, `u16` up to 65535, else `u32`): a cursor a `u8`, a routing key or a path a `u16`, a value or a document a `u32`. A list has a count prefix by the same rule, then its elements. An answer is the op's answer fields the same way, and must decode whole. A body that doesn't decode is refused `bad_request` with `malformed`, `field_too_long` or `out_of_range`, naming the field and the bound it broke, with `ran` = no.

| Op | Request fields | Answer |
|----|----------------|--------|
| `kv_get` | `wait_ms: u64` (default 0, at most 300000), `wait_for: u8` (`0` exists, the default; `1` change), `routing_key?: bytes`, `txn?: u64` | `version: u64`, `value: bytes` |
| `kv_put` | `value: bytes` (at most 253817), `ttl_ms?: u64`, `condition: u8` (`0` always, the default; `1` if_absent; `2` if_present), `cas_version?: u64`, `routing_key?: bytes`, `txn?: u64` | `version?: u64`, absent inside a transaction |
| `kv_delete` | `cas_version?: u64`, `routing_key?: bytes`, `txn?: u64` | `existed?: bool`, absent inside a transaction |
| `kv_scan` | `limit: u32` (1 to 1024), `cursor: bytes` (empty on the first page) | `names: [string]`, `cursor?: bytes`, absent on the last page; a page can hold fewer names than `limit`, even none, while more follow |
| `kv_history` | `limit: u32` (1 to 65, default 10), `before_version?: u64`, `routing_key?: bytes` | `versions: [{version: u64, at_ms: i64, deleted: bool, value: bytes}]`, newest first, `more: bool` |
| `kv_mget` | `keys: [bytes]` (1 to 256), `routing_key?: bytes` | `entries: [{found: bool, version: u64, value: bytes}]`, `next?: u16` |
| `kv_incr` | `delta: i64` (default 1), `routing_key?: bytes`, `txn?: u64` | `version?: u64`, `value?: i64`, both absent inside a transaction |
| `kv_expire` | `ttl_ms: u64` (`0` clears the TTL), `cas_version?: u64`, `routing_key?: bytes`, `txn?: u64` | nothing |
| `kv_exists` | `routing_key?: bytes`, `txn?: u64` | `exists: bool`, `version: u64` |
| `kv_json_get` | `path: string` (default `$`), `routing_key?: bytes` | `version: u64`, `document: bytes` |
| `kv_json_set` | `path: string` (default `$`), `document: bytes` (JSON text), `routing_key?: bytes` | `version: u64` |
| `kv_json_del` | `path: string` (default `$`), `routing_key?: bytes` | `version?: u64`, absent when the path was `$`, which deleted the key |
| `kv_begin_txn` | nothing | `txn: u64`, `pinned: u64` |
| `kv_commit_txn` | `txn: u64` | `commit_index: u64`, `ops: u16` |
| `kv_rollback_txn` | `txn: u64` | nothing |

The key is the envelope's key, except: `kv_scan`'s is the prefix to list (empty for every key); `kv_begin_txn`'s is the routing key the transaction pins, and may not be empty; `kv_mget`, `kv_commit_txn` and `kv_rollback_txn` take an empty key.

`kv_scan` pages across every shard: `cursor` is the previous page's, unchanged. `kv_mget` answers as many keys as fit one response; `next`, when present, is the index of the first key not answered, so the client asks again from there. With `routing_key`, the request is answered on that routing key's shard, where keys written with it live; without, each key is looked up on the shard that owns it. `kv_history` answers versions older than `before_version` when it's given; `more` says older kept versions follow, so the client asks again with `before_version` set to the last version it got. Deleting a missing key isn't an error: it answers `existed` false. `kv_incr` on a value that isn't an 8-byte counter, and the JSON ops on a value that isn't JSON, are refused `bad_request` with `wrong_type`.

`wait_for` exists answers at once if the key exists, else when it's written; change answers the key's next version. Either answers not found when the wait ends with the key absent, and change answers the value still there.

A transaction id is `[shard:u16][counter:u48]`: a request carrying one runs on the shard it names, and on that shard's leader, reads included. An id no shard holds is refused `not_found` with `no_such_transaction`. `kv_commit_txn` and `kv_rollback_txn` route by the id in their body; they need no routing key. Inside a transaction an op must give the routing key it was begun with. `kv_scan`, `kv_mget`, `kv_history` and the JSON ops take no transaction.

### List operations

`stream_list`, `queue_list`, `ts_list`, `namespace_list`, `action_list`, `processing_list` and `workflow_list_definitions` page across every shard. Their request value is:

```
[limit:u32][cursor]
```

`limit` 0, or anything over 1024, is a page of 1024. `cursor` is empty on the first page and otherwise the cursor the previous page returned, unchanged. Every list answer ends with:

```
[has_more:u8][cursor_len:u16][cursor]
```

`worker_list` is declared in the op table: its request is `limit: u32` (1 to 1024, default 1024), `cursor: bytes` (the last id of the page before; empty to start) and `action: bytes` (only workers that run this action; empty for every worker). Its answer is `workers: [{id, worker_type, status, current_load, max_concurrency, tasks_completed, tasks_failed, registered_at_ms, last_heartbeat_ms, machine_id?}]` in id order, then `cursor?: bytes`, absent on the last page.

`workflow_list_runs` takes the workflow's name as its key, or an empty key for every workflow's runs, and pages with its own request value:

```
[limit:u32][status_len:u16][status][cursor_len:u16][cursor][search_len:u16][search]
```

Every field is sent, an empty one with a length of 0. Runs come newest first. `limit` 0 is a page of 100, and anything over 1024 is a page of 1024. Each entry is `[run_id_len:u16][run_id][workflow_len:u16][workflow][status_len:u16][status][created_at:i64]`, and the answer ends like the other lists. A page can hold fewer runs than `limit` while more follow, so keep paging until `has_more` is 0. Pages run newest first from the cursor, so runs started after a listing's first page don't appear in that listing. A malformed cursor is refused `bad_request`.

Paging is not a snapshot. A cursor resumes each shard by name or by position, so names created or deleted between pages can be listed twice or skipped.

## Response

### Header (32 bytes)

| Offset | Field | Type | Description |
|--------|-------|------|-------------|
| 0 | `magic` | `u32` | `0x004F4C46` |
| 4 | `data_len` | `u32` | Bytes of data after the header |
| 8 | `request_id` | `u64` | The request's id |
| 16 | `crc32` | `u32` | CRC-32 of the header (this field excluded) and the data |
| 20 | `version` | `u8` | `0x02` |
| 21 | `status` | `u8` | See [Status codes](#status-codes) |
| 22 | `flags` | `u8` | `0x01` `stale`; no other bit is defined |
| 23 | `_pad` | `u8` | `0` |
| 24 | `table_hash` | `u64` | The hash of the op table the server was built for |

`stale` is set on every answer a [halted shard](/deployment/clustering#a-halted-shard) gives to a read, a not-found included: the read succeeded, from the state just before the entry the shard halted at. It isn't an error.

A response carries no opcode: the client knows which request it sent. Any status but `ok` is a refusal, and its data is a [refusal body](#refusals).

### Versions

The table hash covers every op's request and answer layout and every log entry's. Until an op family is declared in the table, its hand-coded layouts are versioned by an epoch folded into the hash, which every change to one bumps. A server serves only clients carrying its own hash and protocol version; `flo version --verbose` prints both.

A request from another build is answered `bad_request` in the client's own version byte, carrying the server's hash, with a message naming both builds, such as `server table 0x…, client table 0x…: upgrade the client`. Then the connection is closed. The server counts these in `flo_client_version_refused_total`. A client checks an answer's version and hash before reading its data, and refuses an answer from another build.

Nodes built from different tables can't link either: a peer's hello carries the hash. Upgrade by stopping every node, upgrading flo, the CLI and every SDK together, then starting every node.

### Status codes

| Code | Name |
|------|------|
| `0` | `ok` |
| `1` | `error_generic` |
| `2` | `not_found` |
| `3` | `bad_request` |
| `4` | `cross_core_transaction` |
| `5` | `no_active_transaction` |
| `6` | `group_locked` |
| `7` | `unauthorized` |
| `8` | `conflict` |
| `9` | `internal_error` |
| `10` | `overloaded` |
| `11` | `rate_limited` |
| `12` | `unavailable` |
| `13` | `outcome_pending` |

`outcome_pending` is a write that committed but hasn't applied, because its shard halted at it or before it (reason `shard_halted`, `ran` = unknown). The message says which: one past the halt applies when the shard resumes; the one it halted at never runs. Don't resend it unchanged: that writes it twice, or halts again.

### Refusals

Every refusal's data is:

```
[reason:u16][ran:u8][message]
```

The status says whether to retry; the reason says what happened; `ran` says whether the request took effect, so retry logic reads a byte, not text; the message is for a person. A message too long for its frame is cut at a UTF-8 code point and ends `…[truncated]`.

| `ran` | Meaning |
|------|---------|
| `0` `no` | It didn't take effect. |
| `1` `yes` | It took effect: don't resend it. |
| `2` `unknown` | It may still take effect: check before resending. |

| Reason | Name | When |
|--------|------|------|
| `1` | `unknown_op` | The op code names no op this server serves. |
| `2` | `malformed` | The frame or a field isn't what it declares. |
| `3` | `field_too_long` | A field or the request is longer than its bound. |
| `4` | `out_of_range` | A number is outside its range, such as a wait past 5 minutes. |
| `5` | `leader_unknown` | The write found no leader. |
| `6` | `shard_busy` | The shard that owns the request is too busy to take it. |
| `7` | `table_mismatch` | The client was built from another op table or protocol version. |
| `8` | `unknown_flag` | A header flag bit is set; none is defined. |
| `9` | `internal` | A server bug. |
| `10` | `committed_not_applied` | The write committed but this node didn't apply it (`ran` = yes). |
| `11` | `answer_lost` | Its answer couldn't be built or sent. A committed write's lost answer has `ran` = yes; an answer too large to frame has `ran` = unknown. |
| `12` | `unclassified` | From an op family not yet classified; the status and message say what happened. |
| `13` | `not_found` | What the request names doesn't exist. |
| `14` | `reserved_key` | The key is in a prefix the server keeps for itself. |
| `15` | `cas_mismatch` | The write's `cas_version` isn't the key's version. |
| `16` | `condition_failed` | The write's `condition` didn't hold. |
| `17` | `no_such_transaction` | No open transaction has this id here: it committed, rolled back, was begun in another namespace, or never existed. |
| `18` | `wrong_routing_key` | The routing key (the key, when none is given) isn't the one the transaction was begun with. |
| `19` | `txn_too_large` | The transaction holds as many ops or bytes as it may. |
| `20` | `too_many_waiters` | The shard holds as many waiting reads as it may. |
| `21` | `conflicting_fields` | Two fields given together that don't go together, such as a wait inside a transaction. |
| `22` | `writes_stopped` | The shard stopped taking writes: one left memory before it reached disk. It takes them again once the node restarts. |
| `23` | `too_many_proposals` | Too many writes wait for commit. |
| `24` | `wrong_type` | The key's value isn't what the op works on: a counter for `kv_incr`, JSON for the JSON ops. |
| `25` | `too_many_transactions` | The shard holds as many open transactions as it may. |
| `26` | `stale_report` | An action complete or fail for a run that has moved on: another worker holds it, or it finished with another outcome. The report was dropped; resending it is refused the same way. |
| `27` | `worker_unhealthy` | The worker missed its heartbeats and gets no work until it sends one or registers again. |
| `28` | `worker_draining` | The worker is draining and gets no new work. |
| `29` | `shard_halted` | The shard halted at an entry every replica fails the same way. With `unavailable` (`ran` = no) it takes no writes until the entry is repaired, so retrying doesn't help; with `outcome_pending`, see above. |

The reasons are part of the op table, so a client and server that agree on the table hash agree on this list.

## Options

Tags the server reads. An option it doesn't recognise is ignored for now; that changes with the typed op table.

| Tag | Name | Value |
|-----|------|-------|
| `0x05` | `limit` | u32: Maximum results for `ts_read` (earliest first); absent or 0 is all. List operations take theirs in the value |
| `0x10` | `priority` | u8: Message priority (0-255; lower is taken first) |
| `0x15` | `count` | u32: Number of messages to dequeue |
| `0x17` | `block_ms` | u32: Long-poll wait (at most 5 min; 0 = don't wait); a longer one is refused |
| `0x21` | `stream_start` | [16]u8: Read records after this StreamID (exclusive) |
| `0x22` | `stream_end` | [16]u8: End StreamID for reads (inclusive) |
| `0x23` | `stream_tail` | void: Flag indicating tail read (start from end of stream) |
| `0x24` | `partition` | u32: Explicit partition index |
| `0x25` | `partition_key` | string: Key for partition routing |
| `0x26` | `max_age_seconds` | u64: Trim records older than this many seconds |
| `0x27` | `max_bytes` | Refused: byte-based trim isn't supported ([#183](https://github.com/floruntime/flo/issues/183)) |
| `0x28` | `dry_run` | void: Trim answers what it would remove and removes nothing |
| `0x29` | `retention_count` | u64: Retention policy - max event count |
| `0x2A` | `retention_age` | u64: Retention policy - max age in seconds |
| `0x2B` | `retention_bytes` | Refused: byte retention isn't supported ([#183](https://github.com/floruntime/flo/issues/183)) |
| `0x2C` | `force` | void: Force a destructive op (e.g. delete a non-empty stream) |
| `0x30` | `ack_timeout_ms` | u32: Time before unacked message auto-redelivers (overrides default) |
| `0x31` | `max_deliver` | u8: Max delivery attempts before DLQ (default: 10, 0=unlimited) |
| `0x60` | `ts_from_ms` | i64: Start of time range (inclusive, unix ms) |
| `0x61` | `ts_to_ms` | i64: End of time range (inclusive, 0 = now) |
| `0x62` | `ts_window_ms` | i64: Aggregation window size (ms) |
| `0x63` | `ts_aggregation` | string: Aggregation function name (avg, sum, count, min, max) |
| `0x64` | `ts_field` | string: Field name filter (empty = "value") |
| `0x65` | `ts_tags` | string: Comma-separated tag filters "key=val,key2=val2" |
| `0x67` | `ts_timestamp` | i64: A write's timestamp in ms; absent, 0 or less = the server's clock |
| `0x68` | `ts_raw_ttl` | string: Raw data TTL (e.g., "7d") |
| `0x69` | `ts_downsample` | string: refused — downsampling isn't supported ([#158](https://github.com/floruntime/flo/issues/158)) |
