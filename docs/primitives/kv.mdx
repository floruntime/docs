---
title: KV
lede: Strongly consistent, versioned key-value storage with CAS, TTL, blocking gets, and namespace isolation.
---

Flo's KV store provides strongly consistent key-value storage backed by the Unified Append Log. Every write is Raft-replicated across the cluster before being acknowledged. Reads go directly to the local projection — no Raft round-trip, no cross-node hops for single-key lookups.

## Core Concepts

### Versioned Writes

Every mutation to a key creates a new **version**: 1 on its first write, one more on each after.

Put responses include the new version number, which you can use for subsequent CAS updates:

```bash
flo kv set counter "1"                   # → OK version=1
flo kv set counter "2" --cas-version 1   # → OK version=2
flo kv set counter "3" --cas-version 1   # → Error: conflict: cas_version isn't the key's version [conflict/cas_mismatch]
```

### Namespace Isolation

Keys live inside **namespaces**. The default namespace is used when no `-n` flag is provided. Keys with the same name in different namespaces are fully independent — they have separate values, versions, and TTLs.

```bash
# Create namespaces
flo ns create staging
flo ns create production

# Same key, different namespaces
flo kv set db_url "postgres://staging" -n staging
flo kv set db_url "postgres://prod"    -n production

# Each returns its own value
flo kv get db_url -n staging      # → postgres://staging
flo kv get db_url -n production   # → postgres://prod
```

Deleting or overwriting a key in one namespace has no effect on the same key in other namespaces. Conditions like `--condition if_absent` are also per-namespace — a key can be "new" in one namespace while already existing in another.

## Operations

### Put

```bash
flo kv set mykey "hello world"
```

| Flag | Description |
|------|-------------|
| `--ttl-ms <ms>` | Expire after this long: milliseconds, or a number and a unit (`500ms`, `30s`, `5m`, `1h`, `1d`); `0` = no expiry |
| `--condition <when>` | `always` (the default), `if_absent` (only if the key does **not** exist) or `if_present` (only if it **does**) |
| `--cas-version <version>` | Only set if the key's version is exactly this |
| `-n <namespace>` | Target namespace |
| `-r <routing-key>` | Explicit shard routing key for co-location |
| `-t <txn-id>` | Buffer the write in a transaction |

A condition and a version may be given together; the write happens only if both hold.

**CAS version 0** has a special meaning: it asserts the key must not exist yet. This is equivalent to `--condition if_absent` but expressed as a version constraint.

### Get

```bash
flo kv get mykey
flo kv get mykey -o json   # includes version number
```

| Flag | Description |
|------|-------------|
| `--wait-ms <ms>` | How long to wait: milliseconds, or a number and a unit (`500ms`, `30s`, `5m`); at most `5m`; `0` does not wait; a longer wait is refused |
| `--wait-for <what>` | What to wait for: `exists` (the default) or `change` |
| `-o <fmt>` | Output format: `json`, `table`, `raw` |
| `-n <namespace>` | Target namespace |
| `-r <routing-key>` | Explicit shard routing key |
| `-t <txn-id>` | Read inside a transaction, seeing its buffered writes |

The two kinds of wait serve different purposes:

- **`--wait-for exists`** is for coordination — one process creates a key, another waits for it to appear. If the key already exists, it returns immediately.
- **`--wait-for change`** is for watching — subscribe to the next change on an existing key. Even if the key exists now, it waits for a newer version. If nothing changes in time, it returns the current value with its unchanged version, so a watcher can compare and ask again; a key that is gone returns not found.

```bash
# Process A: wait for a result to appear
flo kv get job:result --wait-ms 30s

# Process B: watch for config changes
flo kv get config:feature-flags --wait-ms 5m --wait-for change
```

### Multi-key get

Fetch many keys in one request. Keys may live on different shards — the server looks each up on the shard that owns it and returns one entry per requested key, in order (with a `found` flag distinguishing missing keys from empty values).

```bash
flo kv mget user:1 user:2 user:3
flo kv mget user:1 user:2 --output json
flo kv mget user:42:name user:42:visits -r user:42   # keys written with -r user:42
```

Keys written with a routing key live on its shard: read them with the same routing key, which applies to every key in the call. An mget reads each key as it stands when it gets there: it isn't one snapshot across shards.

| Flag | Description |
|------|-------------|
| `-r, --routing-key <key>` | The routing key every key was written with: all are read from its shard |
| `--output <fmt>` | `text` (default), `json`, `table` |
| `-n <namespace>` | Target namespace |

Limited to **256 keys per call**. One answer holds about 256 KiB; when the values don't fit, the server answers what does and says where it stopped, and the CLI and SDKs ask again for the rest on their own.

### Delete

```bash
flo kv delete mykey
```

Aliases: `del`. Deleting a key that doesn't exist succeeds: it prints `OK existed=false`, and `OK existed=true` when there was one to delete.

| Flag | Description |
|------|-------------|
| `-n <namespace>` | Target namespace |
| `-r <routing-key>` | Explicit shard routing key |

### List / Scan

```bash
flo kv list                      # all keys
flo kv list --prefix "user:"     # prefix filter
flo kv list --limit 50           # cap results
```

Aliases: `ls`, `scan`.

| Flag | Description |
|------|-------------|
| `--prefix <p>` / `-p` | Filter by key prefix |
| `--limit <n>` / `-l` | Max keys to return (default: 100) |
| `-n <namespace>` | Target namespace |

List returns names only; read values with `get` or `mget`. It walks **all shards** — keys are returned regardless of which shard they hash to — a page of up to 1024 names at a time, resuming from the previous page's cursor. The prefix filter is applied on each shard locally before results are merged.

### Version History

```bash
flo kv history mykey
flo kv history mykey --limit 5
```

Aliases: `hist`. Returns previous values, newest first, each with its version and the time it was written in Unix milliseconds. History for a key with none returns not found (exit 1).

| Flag | Description |
|------|-------------|
| `--limit <n>` / `-l` | Max entries, 1 to 65 (default: 10) |
| `-r <routing-key>` | Explicit shard routing key: give the one the key was written with |
| `-n <namespace>` | Target namespace |

Flo maintains a bounded version chain per key (default depth: 64). Oldest versions are evicted when the chain is full. Deletes create tombstone entries — prior versions remain queryable through history even after deletion.

## TTL (Time-to-Live)

Set an expiration on keys:

```bash
flo kv set session:abc '{"user":"alice"}' --ttl-ms 1h
```

The key expires one hour after the write. Expired keys return `(nil)` on get, as if they were never written. Setting `--ttl-ms 0` explicitly means "no expiration."

TTLs are milliseconds, with millisecond resolution. `--ttl-ms` takes a bare number of milliseconds, or a number and a unit — `ms`, `s`, `m`, `h` or `d`, as in `500ms` or `1d`. `kv expire` takes the same.

Overwriting a key **resets its TTL**. If you set a key with `--ttl-ms 60s` and then overwrite it without a TTL, the new value has no expiration:

```bash
flo kv set temp "short-lived" --ttl-ms 5s   # expires in 5s
flo kv set temp "permanent"                 # TTL cleared
```

TTL combines with conditions. A common pattern is a TTL with `--condition if_absent` for "set once with expiry":

```bash
flo kv set lock:resource "owner-1" --ttl-ms 30s --condition if_absent
```

Expiry is **lazy** — keys are checked at read time rather than proactively swept. This means expired keys don't consume I/O until accessed.

## Compare-and-Swap (CAS)

CAS enables optimistic concurrency control. Read the current version, then conditionally write only if nobody else has modified the key since:

```bash
# Step 1: read current value and version
flo kv get counter -o json
# {"key":"counter","value":"41","version":7}

# Step 2: update only if version is still 7
flo kv set counter "42" --cas-version 7
```

If another writer updated the key between your read and write, the CAS fails with `[conflict/cas_mismatch]` (exit 3) and the original value is preserved.

**CAS works across the cluster.** You can read the version on one node and CAS-update through another: every write goes to the leader, which checks the version against what it has applied when the write arrives. In a cluster, two writes carrying the same version that arrive before either has committed can both pass, so CAS guards against a stale read; it is not yet a lock between concurrent writers.

## Atomicity model

Flo's KV store is built around **per-key linearizable writes** rather than multi-key transactions. Every mutation goes through Raft as a single committed entry, so each individual operation is atomic and durable on its own — the same model used by etcd, Consul, and FoundationDB single-key paths.

### Conditional & atomic writes

Use the conditional flags on `kv set`/`KV.Put` to express "do this only if X". Each is a single Raft entry — no coordinator, no roundtrips, no rollback to worry about.

| Pattern | How |
|---------|-----|
| Insert if absent | `--condition if_absent` (or `--cas-version 0`) |
| Update only if present | `--condition if_present` |
| Compare-and-swap by version | `--cas-version <version>` |
| Atomic create with lease | `--condition if_absent --ttl-ms <duration>` |
| Atomic counter | [`kv incr`](#counters) |
| Atomic JSON sub-field update | [`kv jset`](#json-paths) |

The classic read-modify-write loop becomes:

```bash
# 1. Read current state and version (PUT/GET both return the version)
flo kv get account:42 -o json     # → value + version=11

# 2. Compute new state client-side
# 3. Conditional write — fails if anyone else changed the key
flo kv set account:42 '{"balance":150}' --cas-version 11
```

If the CAS fails, re-read and retry. For a counter, prefer `kv incr` — it is unconditional and never conflicts.

#### CAS-guarded delete and expire

The same version guard is also accepted by `delete` and `expire`. This closes the classic distributed-lock race: the holder can release the lock (or extend its lease) only if it still owns the version it acquired.

```go
// Acquire: a put-if-absent with a 30 s TTL returns version
ttl := uint64(30_000)
v, _ := client.KV.Put("lock:job-42", []byte(ownerID),
    &flo.PutOptions{Condition: flo.ConditionIfAbsent, TTLMs: &ttl})

// ... do work ...

// Release: only the owner deletes — no risk of unlocking after expiry
_, _ = client.KV.Delete("lock:job-42", &flo.DeleteOptions{CASVersion: &v.Version})
```

```python
v = await client.kv.put("lock:job-42", owner_id.encode(),
    PutOptions(condition=Condition.IF_ABSENT, ttl_ms=30_000))
# ... work ...
# Renew the lease atomically
await client.kv.expire("lock:job-42", 30_000, KVExpireOptions(cas_version=v.version))
# Release: only the owner deletes
await client.kv.delete("lock:job-42", DeleteOptions(cas_version=v.version))
```

A version mismatch is refused with `[conflict/cas_mismatch]`, as `set` with `--cas-version` is; re-read to decide whether to retry or give up.

### Multi-key atomicity

For multi-key writes that must commit or fail as a unit, Flo offers [**per-shard transactions**](#transactions). Operations are buffered on a single pinned partition and replicated as one Raft entry on commit. Pick the right tool:

| Need | Recommended approach |
|------|---------------------|
| "Several keys, all-or-nothing" | Open a [transaction](#transactions) pinned to a routing key — all writes commit atomically as one Raft entry. |
| "All these keys live together" | Set the same `--routing-key` on every related key (see [Shard Co-location](#shard-co-location)). Reads and writes stay on one shard. |
| "Update several fields of one document" | Model the state as a **single key with a JSON value** and use [`kv jset`](#json-paths) or CAS on the whole document. One Raft entry, no coordination. |
| "Atomic counter" | Use [`kv incr`](#counters) — unconditional and conflict-free. |
| "Long-running multi-step state machine" | Use a [workflow](/orchestration/workflows). Workflows give you durable execution, retries, and compensation steps. |
| "Idempotent producer / exactly-once write" | Use `--condition if_absent` on a dedupe key (e.g. `dedupe:<request-id>`) before doing the work. |
| "Cross-partition transaction" | Not supported. Either restructure keys to share a routing key, or use a workflow with compensating actions. |

## Counters

`kv incr` (opcode `0x10B`) atomically adds a signed delta to a key holding a 64-bit counter. The first `incr` on a missing key creates it at the delta value. The operation is unconditional — it never conflicts — and is ideal for rate-limit buckets, sequence generators, and metric accumulators.

```bash
flo kv incr visits:home          # +1, returns new value
flo kv incr visits:home -d 10    # +10
flo kv incr visits:home -d -1    # decrement
```

A counter and a string value cannot share a key. `incr` against a key whose value isn't an 8-byte counter is refused with `[bad_request/wrong_type]` (exit 3). Inside a transaction `incr` prints `OK`: the new value isn't known until commit.

### Recipe: per-minute rate limiter

```python
minute = int(time.time() // 60)
key = f"rl:{user_id}:{minute}"
count = (await client.kv.incr(key)).value
if count == 1:
    await client.kv.expire(key, 120_000)  # auto-expire old buckets
if count > LIMIT:
    raise RateLimited()
```

## TTL lifecycle

TTLs are set at write time via `--ttl-ms` / `PutOptions.TTLMs`, but you can also adjust them later:

| Op | Effect |
|----|--------|
| `kv expire <key> --ttl-ms <duration>` | Set the TTL on an existing key, from now, without rewriting the value |
| `kv expire <key> --ttl-ms 0` | Clear the TTL: make the key permanent |

`expire` takes `--cas-version`, `-r` and `--txn` like `delete`; a missing key is not found (exit 1).

Each is a single Raft entry. Use it to extend session leases, refresh distributed locks, or promote a temporary value to permanent without losing it.

## Existence check

`kv exists` (opcode `0x115`) answers whether the key exists, and its version, without transferring the value, so it is much cheaper than `get` for large values.

```bash
flo kv exists user:123    # prints 1 version=<n> and exits 0 if present; prints 0 and exits 1 if absent
```

## JSON paths

For keys whose value is a JSON document, three operations let you read or mutate **sub-fields** without round-tripping the whole document:

| Op | Wire | Purpose |
|----|------|---------|
| `kv jget <key> [--path <path>]` | `0x10C` | Extract `path` from the JSON document. Path defaults to `$` (the whole document). |
| `kv jset <key> <document> [--path <path>]` | `0x10D` | Atomically set the value at `path`. `$` replaces the document (and creates the key if missing); any other path needs an existing document. |
| `kv jdel <key> [--path <path>]` | `0x10E` | Remove the value at `path`. `$` deletes the key. |

Paths use a tiny JSONPath subset: `$`, `.field`, `.field.nested`, `[index]`. The operations are atomic per Raft entry — a sub-field update is a single committed write, not a read-modify-write loop.

The answer to `jget` carries the document's current `version` alongside the JSON; `jset` and `jdel` answer the new version (`jdel` at `$` answers none, since the key is gone). Use that version to drive CAS on subsequent writes. A path with nothing at it is not found (exit 1); a key whose value isn't JSON is refused with `wrong_type`. The JSON ops don't run inside transactions.

### Recipe: status enrichment

```bash
flo kv set order:42 '{"id":42,"items":3,"status":"new"}'
flo kv jset order:42 '"shipped"' --path '$.status'
flo kv jget order:42 --path '$.status'      # → "shipped"
```

The `jset` is a single Raft entry; concurrent writers updating different fields on the same document still each succeed atomically (last writer wins per field).

## Transactions

Per-shard transactions buffer multiple writes on a single pinned partition and commit them atomically as **one Raft entry**. Open with a routing key, and give that routing key with every op inside the transaction (`-r`); an op with another is refused with `wrong_routing_key`. The transaction id names its shard, so `commit` and `rollback` take nothing else.

| Op | Wire | Purpose |
|----|------|---------|
| `kv begin -r <routing-key>` | `0x110` | Open a new transaction. Returns a `txn_id` and the partition's `pinned_hash`. |
| `kv commit <txn-id>` | `0x111` | Apply all buffered ops atomically. Returns the op count and the `commit_index`. |
| `kv rollback <txn-id>` | `0x112` | Discard buffered ops. A transaction that isn't open (already committed, rolled back or dropped as idle) is refused with `no_such_transaction`. |

Inside a transaction, `set`, `get`, `delete`, `incr`, `expire` and `exists` accept a `--txn <id>` flag; writes are buffered until commit. **Reads inside the transaction see the buffered writes.** `list`, `mget`, `history` and the JSON ops take no transaction.

**Server caps**: 256 ops per transaction, 1 MiB total payload, 1024 open transactions per shard (past that, `begin` is refused with `too_many_transactions`).

```bash
# Open (prints txn_id=<id> pinned_hash=<hash>), write, commit
TXN=$(flo kv begin -r user:42 | sed 's/txn_id=\([0-9]*\).*/\1/')
flo kv set user:42:name "Jane"   -r user:42 --txn $TXN
flo kv incr user:42:visits       -r user:42 --txn $TXN
flo kv set user:42:last_seen "$(date -u +%s)" -r user:42 --txn $TXN
flo kv commit $TXN               # → OK ops=3 commit_index=N
```

Transactions survive across stateless connections — they are owned by `txn_id`, not by the TCP connection. So a transaction that goes **30 seconds without a request** is dropped with its buffered ops, freeing its slot when a client crashes before commit; any request in it, even one refused, counts as use. A later request on a dropped transaction is refused with `no_such_transaction`, and nothing of it is written. `flo_kv_txns_reaped_total{shard_id}` counts the drops.

### When to use transactions vs. JSON or workflows

| Pattern | Use |
|---------|-----|
| Atomic update of 2–10 related keys on the same partition | **Transaction** |
| Atomic update of fields inside one document | [`kv jset`](#json-paths) |
| Atomic counter increment | [`kv incr`](#counters) |
| Multi-step business process across shards / external systems | [Workflow](/orchestration/workflows) |

## Shard Co-location

By default, each key is routed to a shard based on its hash. When you need related keys to land on the same shard (for locality or future atomic operations), use `--routing-key`:

```bash
flo kv set user:123:name "Alice" -r "user:123"
flo kv set user:123:email "alice@co.io" -r "user:123"
flo kv set user:123:prefs '{"theme":"dark"}' -r "user:123"
```

All three keys route to the same shard because they share the routing key `user:123`.

## Cluster Behavior

In a multi-node cluster:

- **Writes** are proposed to the Raft leader and replicated to a majority before being acknowledged.
- **Reads** are served from the local shard's projection — no Raft round-trip needed.
- **Data replicates** to all nodes. A key written on node 1 is readable from node 2 and node 3 after replication.
- **Node failures** are tolerated as long as a majority (quorum) of nodes remain healthy. A 3-node cluster survives 1 node failure.
- **CAS and conditional writes** are consistent across the cluster — the version check happens at the leader during Raft proposal.

    await client.kv.json_set("order:42", "$.status", b'"shipped"')
    status = await client.kv.json_get("order:42", "$.status")

    # Wait up to 5 s for the key to appear
    r = await client.kv.get("job:result", GetOptions(wait_ms=5000))

    # Prefix scan
    result = await client.kv.scan("user:", ScanOptions(limit=100))
    for name in result.names:
        print(name)
    # result.cursor is None on the last page; pass it in ScanOptions(cursor=...) for the next

    # Version history
    history = await client.kv.history("counter", HistoryOptions(limit=5))
    for v in history:
        print(f"v{v.version}: {v.value} (at {v.at_ms} ms)")

    # Namespace-scoped
    await client.kv.put("config", b"staging-db",
        PutOptions(namespace="staging"))

    # Transaction — multiple writes on one shard, atomic commit
    txn = await client.kv.begin("user:42")
    try:
        await txn.put("user:42:name", b"Jane")
        await txn.incr("user:42:visits")
        result = await txn.commit()
        print(f"committed {result.op_count} ops at index {result.commit_index}")
    except Exception:
        await txn.rollback()  # idempotent
        raise

## Use Cases

### Distributed Locks

Use `--condition if_absent` with `--ttl-ms` as a simple distributed lock with automatic expiry:

```bash
# Acquire lock (fails if already held)
flo kv set lock:payment "worker-7" --ttl-ms 30s --condition if_absent

# Release lock
flo kv delete lock:payment
```

The TTL acts as a safety net — if the lock holder crashes, the lock auto-expires.

### Configuration Store

Store configuration per environment using namespaces, and watch for changes with `--wait-for change`:

```bash
# Set config
flo kv set feature:dark-mode "true" -n production

# Watch for config changes (long-poll)
flo kv get feature:dark-mode --wait-ms 5m --wait-for change -n production
```

### Job Coordination

Use `--wait-ms` for producer/consumer coordination where one process publishes a result and another waits for it:

```bash
# Worker: process job and publish result
flo kv set job:abc:result '{"status":"done","output":"..."}' --ttl-ms 1h

# Requester: wait for result (up to 60 seconds)
flo kv get job:abc:result --wait-ms 60s
```

## Internals

The KV store is implemented as a **KV Projection** — a hash table with MVCC version chains, derived from the Unified Append Log.

| Property | Value |
|----------|-------|
| Max key size | ~3.9 KB |
| Key bytes | Any except NUL (`0x00`), which is refused |
| Max value size | ~256 KB |
| Max namespace length | 63 bytes |
| Version chain depth | 64 versions per key (oldest evicted) |
| Default list limit | 100 (pages of up to 1,024) |
| Reserved key prefixes | `_action:`, `_worker:`, `_sys:`, `_internal:`, `_flo:` |

**Write path**: `kv_put` → Raft propose → majority commit → UAL append → KV projection update → response to client.

**Read path**: `kv_get` → KV projection lookup → response. No Raft involvement.

**Recovery**: On server restart, the projection is rebuilt by replaying UAL entries from the last snapshot. Read-after-write consistency is immediate after recovery — there is no warm-up period.

**TTL enforcement**: Lazy — expired keys are detected at read time rather than proactively swept. This avoids background I/O for expiry.

**Tombstones**: Deletes write a tombstone entry to the UAL. Prior versions remain in the version chain and are queryable via `history`. Tombstones are purged during compaction.
