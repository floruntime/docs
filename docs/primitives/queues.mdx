Flo queues distribute tasks to competing consumers with priority ordering and dead-letter handling. Every change to a queue — an enqueue, a dequeue, a complete, a fail, a lease running out — is a Raft-replicated log entry, so every replica, a restarted node and a new leader hold the same messages and leases.

## Core Concepts

### Leases and Deliveries

A dequeue **leases** its messages to the consumer that took them; it doesn't remove them. The consumer then, within the lease:

- **completes** (acks) them: they leave the queue;
- **fails** (nacks) them: they're ready again, after an optional delay, or dead once their attempts are spent;
- **touches** them: their lease runs on.

A lease that runs out makes its messages ready again, and the next dequeue takes them as their next delivery. Delivery is **at-least-once**: a consumer that crashes before completing gets its messages handed to another consumer once the lease runs out.

Each dequeue is one **delivery**, named by the term and log index it was made at. Every message in it is named back by its seq and its delivery count. The CLI prints a message's delivery as `term.index.seq.deliveries`, which `ack`, `nack` and `touch` take. A report naming an older delivery — one whose lease ran out and whose messages went to someone else — applies nothing, and is refused message by message with a reason.

The default lease is 30 seconds; a dequeue may name its own, from 5 seconds to 12 hours. A touch with half the lease or less left runs a full lease from then, up to 12 hours from the dequeue.

### Sequence Numbers

Every message is assigned a monotonically increasing **sequence number** in its queue on enqueue. The enqueue answers it.

### Priority Ordering

Messages are dequeued in priority order. Lower numeric values are higher priority (0 is highest). Within a priority, messages go in the order they became ready, then by sequence: one failed with a delay goes behind those ready before it. A priority whose next message isn't due yet doesn't hold back the next priority's ready messages.

```bash
flo queue enqueue tasks '{"urgent":true}' --priority 1
flo queue enqueue tasks '{"routine":true}' --priority 10

# Dequeue returns the priority-1 message first
flo queue dequeue tasks
```

Priority is a `u8` value (0–255).

### Namespace Isolation

Queues live inside **namespaces**. The same queue name in different namespaces is fully independent — separate messages, separate DLQ, separate statistics.

A command names its namespace with `-n`/`--namespace`, or with the `FLO_NAMESPACE` environment variable when `-n` isn't given (default `default`); an SDK client sets it in its options:

```bash
flo queue enqueue tasks '{"env":"staging"}' -n staging

export FLO_NAMESPACE=production
flo queue enqueue tasks '{"env":"prod"}'
# Each namespace has its own "tasks" queue
```

## Operations

### Enqueue

```bash
# Basic enqueue
flo queue enqueue tasks '{"task":"send-email","to":"alice@example.com"}'

# With priority (lower = higher priority, default: 0)
flo queue enqueue tasks '{"urgent":true}' --priority 1

# Ready in a minute, not now (at most a day)
flo queue enqueue reminders 'ping' --delay 60000
```

The response returns the assigned sequence number. A message takes at most 64 KiB. A deduplication key is refused: a queue keeps no deduplication window.

### Dequeue

```bash
# Take one message (default count: 1), leased for 30 s
flo queue dequeue tasks

# Up to 10 at once (max: 100), leased for 2 minutes, by a named consumer
flo queue dequeue tasks --count 10 --lease 120000 --consumer worker-1

# Take them for good: completed as they're taken, payloads only
flo queue dequeue tasks --ack
```

Each line is a message's delivery, then its payload:

```
3.42.7.1 {"task":"send-email","to":"alice@example.com"}
```

`-o json` prints the delivery's term, index and lease expiry, and each message with its delivery. `-o raw` prints payloads only, so it is refused without `--ack`: nothing could ack what it printed.

With `--ack`, the dequeue is answered once its complete applies. If that can't be confirmed — the leader changes in between — its messages are answered as an ordinary dequeue's, leased with their delivery: they're never lost, and acking them later answers `gone` (already done) if the complete landed, or completes them if not.

A consumer named with `--consumer` must name itself the same in `ack`, `nack` and `touch`. Without one, consumers share the empty name; the delivery's term and index alone then decide whose report applies, which is enough, since no two deliveries share them.

### Blocking Dequeue

If the queue has nothing ready, a blocking dequeue waits for a message instead of returning at once.

```bash
# Block up to 30 seconds for new messages
flo queue dequeue tasks --block 30000

# The longest wait the server allows: 5 minutes (a longer one is refused;
# 0 does not wait)
flo queue dequeue tasks --block 300000
```

An enqueue wakes one waiting dequeue per message it makes ready; the rest keep waiting. If the wait runs out with no messages, an empty (but successful) result is returned. A wait on a queue holding only delayed messages is woken within about a second of the first coming due.

### Complete (Ack)

```bash
flo queue ack tasks 3.42.7.1

# Several messages of the same dequeue
flo queue ack tasks 3.42.7.1 3.42.8.1
```

Each message applies or is refused on its own. A refused one is printed with its reason, and the command exits non-zero:

| Reason | Means |
|--------|-------|
| `gone` | No such message in this queue. For a complete, this means done: a resent ack whose first applied finds its messages gone. |
| `delivered_again` | Its lease ran out or it was failed, and it was dequeued again: this delivery is over. |
| `other_holder` | Another consumer holds this delivery. |
| `expired` | Its lease ran out; it is ready again, or dead. |
| `released` | It was failed; it is ready again, or dead. |
| `not_held` | It isn't leased. |

### Fail (Nack)

```bash
# Ready again at once
flo queue nack tasks 3.42.7.1

# Ready again in 10 seconds, with a reason kept on the message
flo queue nack tasks 3.42.7.1 --delay 10000 --error "upstream timed out"

# Dead now, whatever attempts are left
flo queue nack tasks 3.42.7.1 --dlq
```

A message failed, or whose lease ran out, 5 times is dead.

### Touch

```bash
flo queue touch tasks 3.42.7.1
```

Keeps a long job's messages: with half their lease or less left, it runs a full lease from now; with more left, nothing changes. Touch at least every half lease.

### Peek

Inspect the next ready messages, in the order a dequeue takes them, without taking them:

```bash
flo queue peek tasks --limit 5
```

### List Queues

```bash
flo queue ls
flo queue list --limit 50 -o json
```

Returns each queue's name, namespace, ready and leased counts, total enqueued, total delivered, and dead count.

### Watch

Continuously take and print messages as they arrive, completing each:

```bash
flo queue watch tasks
```

## Dead Letter Queue

A message failed or expired 5 times, or failed with `--dlq`, is dead. Dead letters are kept until the queue is purged, and count towards what the queue holds.

```bash
# List DLQ messages, oldest first
flo queue dlq list tasks
flo queue dlq list tasks --limit 50
```

Each DLQ entry records the sequence number, its delivery count, and when it died. Requeueing and deleting dead letters aren't supported yet.

## Limits

A queue holds at most 100,000 messages and 256 MiB of payloads, ready, leased and dead together, and all of a shard's queues together 1 GiB. Past either, an enqueue is refused `overloaded`:

```text
overloaded: queue 'tasks' is full: it holds 100000 messages (at most 100000) and 52428800 payload bytes (at most 268435456), ready, leased and dead; consume or purge it
```

Nothing already held is dropped. Consume messages, or purge the queue, to make room. The caps are [`[queues]` settings](/getting-started/configuration/#queues).

## Dequeue Answer

A dequeue answers the delivery's `term` and `index`, `expires_at_ms` (when the lease runs out; 0 when nothing was taken, or with ack), and each message:

| Field | Description |
|-------|-------------|
| `seq` | Sequence number, increasing per queue |
| `payload` | The message body (bytes) |
| `priority` | Priority value (0–255, lower = higher priority) |
| `enqueued_at_ms` | When the message was enqueued |
| `deliveries` | Its deliveries, this one included |

## Durability

- Every enqueue, dequeue, complete, fail, touch and lease expiry is a Raft-replicated log entry, applied alike on every replica.
- A leader that fails mid-lease leaves the lease to the next one, which gives it a grace of up to 30 seconds past its deadline before ending it, so a consumer that touched the old leader in time isn't cut off.
- A dequeue whose client is gone when it's answered leaves its messages leased until the lease runs out.
- Unconsumed messages and leases survive restarts, rebuilt from the log.

## How It Works

A queue is kept as a few ordered families in each shard's state:

- **Messages** — each message's payload, priority, status (ready, leased or dead), delivery count and current lease. A ready message costs its payload plus about 340 bytes of memory.
- **Ready keys** — ordered by `(priority, due time, seq)`, so the next message is the first key.
- **Deadlines** — every lease's expiry, earliest first, which the leader's expire duty reads every second.
- **Dead letters** — oldest first, kept until the queue is purged.

A dequeue logs a deliver; every replica applies it by leasing the first due ready messages, so they all lease the same ones.
